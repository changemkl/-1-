# 自动更新展示系统

腾讯文档提供客户名称、稳定客户编号和分类。名单变更、来源状态、采购资料、机构和领导信息独立保存，不写回在线表格。

## 更新流程

- `Sync Tencent spreadsheet` 约每 5 分钟读取官方 API；GitHub 调度和前一轮采集可能造成延迟。网页每分钟读取已发布名单。没有变更的定时检查不重复发布站点。
- 同步后执行 `intelligence/customer_system.py`：新增编号生成客户记录；同编号改名保留历史名称并重新核对来源；删除客户归档；重新加入同编号可恢复历史资料。有效表头且无客户行表示清空名单；API 异常、缺少表头、重复编号对应不同名称时保留上次名单。
- 新增、改名、归档等生命周期变化自动排队执行资料采集。每小时还有一次常规采集；已适配的官网领导名单每 24 小时复查。
- 来源优先按精确名称匹配已核实来源库，再尝试政府官网导航与公开搜索列表。只有 gov.cn 上标题精确匹配单位名称、且具备政府网站/公开栏目依据的主页可以自动采用。企业候选网站和身份不明确的网站保留待核实，绝不仅凭搜索排名确认官网。通用搜索可能禁止自动读取，不绕过限制。
- 新的已核实来源自动进入有界官网采集；采购还会按完整客户名称查询上海政府采购公开范围。其他地区和企业自建平台需要有明确来源，不能视作已覆盖。每轮最多处理 12 个已核实来源、3 个待核实客户采购查询、3 个新来源发现，按检查时间轮转。
- 官网页面明确列出的内设机构、姓名、现任职务和分工可以形成结构化资料。未识别的格式留空，不生成部门、决策人或商机。已人工整理的完整机构资料优先保留；新客户可显示采集得到的机构树。
- 采购只展示标题和日期；明确过期的采购意向和投标截止时间不展示。标题能确认是往年意向时，即使刚被重新读取也不会当作新意向。

## 客户卡片排序与补充

客户卡片优先展示已有可核实内容的单位，同组按公开条目数量倒序；采购项目、领导记录、机构资料、历史结果和有来源的业务概况均计入。仅确认官网入口不算已补充业务资料。

业务概况与机构、地址保存在独立的 organization-data.json 中，保留 basicSource/source/sources。资料允许来自单位官网或明确提及该单位的政府公开报道；不能将报道中的监管部门领导或监管部门机构当作企业人员和部门。当前新增企业的政府报道来源禁止抓取该政府网站本级的领导、机构资料。市数据局、市教委、应急管理局和市委党校已适配公开领导页面的定期复核。

“刷新客户”同时重新读取已发布的机构、领导和历史结果。卡片侧栏按稳定客户编号打开，排序变化时不会按旧位置打开其他客户。

## 历史招标结果

卡片“组织架构”下方的“历史招标结果”按钮打开独立侧栏，按结果公告发布日期倒序列出标题与原文链接，关联单位明确显示采购单位。中标/成交结果不再混入当前采购机会列表。

`python intelligence/award_history.py` 定时读取上海市政府采购网近三年的公开结果列表；核对采购人名称，排除更正、废标、取消、合同和网上超市公告，不访问需登录的详情。每家最多读取 4 页，每轮最多轮转 8 家客户。侧栏明确显示查询范围及分页限制，其他渠道暂无记录不代表不存在历史采购。读取失败保留旧记录；历史结果与当前机会独立保存。

## 存储与恢复

- `public/award-history.json`：历史结果标题、公告日期、实际采购单位、原文链接和读取状态。
- `public/tencent-data.json`：名单快照，不含 API 凭证。
- `public/customer-system.json`：稳定编号、历史名称、是否启用、已核实/候选来源、发现状态。
- `public/customer-archive.json`：移出名单时的画像、组织和领导快照，不级联删除资料。仅保留公开业务信息。
- `public/profile-data.json`：采购、通用领导和机构提取的独立快照。
- `public/organization-data.json`、`public/people-data.json`：已核实的机构资料和适配过的官网领导名单。

数据库在 GitHub Actions 中为临时 SQLite，长期展示资料保存于上述 JSON 和 Git 提交历史。本展示版不需要新增 Cloudflare 或收费数据库。采集失败保留原始记录及原核对日期；改名且来源仍待核实期间不展示原单位资料，避免混入新单位。

保留腾讯表格现有“集团编号/客户编号”列。缺少编号时按名称关联，改名会被视为新客户，无法可靠恢复同一客户身份。新企业来源经核实后，在 `intelligence/sources.json` 加入准确名称别名和官网地址即可自动进入后续流程；不需要改前端卡片。

# 客户公开信息采集与独立画像库

## 数据边界

腾讯表格同步客户名称和分类，保留集团编号作为稳定关联键；行业分类优先于企业性质，采购与组织画像仍由独立资料库维护，不从表格导入等级、地区或画像。同一集团编号改名不覆盖已有画像。若没有稳定编号，使用名称作为键，改名将被视为新客户；建议保留集团编号。删除客户只停用名单，不级联删除历史资料。

画像、标签、原文摘录、来源、发布时间、采集时间、历史版本、任务状态均存储在独立 SQLite / Cloudflare D1 数据库，不放回在线表格。库表位于 schema.sql。采集器只产生待核实动态，不自动声称“痛点、决策链、可售能力、竞争对手、下一步动作”。这些字段单独保存在 profile_attributes，只接收人工维护或审核后的结果；采集任务不覆盖它们。

## 已实现与限制

- 允许列表中的 HTTPS 公开来源、robots.txt 检查、同域链接、请求超时、单页大小限制、每来源最多 3 篇、请求间隔 1 秒。
- 基于标题的确定性分类：采购、数字化、规划、人事、经营动态。不是全网搜索，也没有调用收费 AI 接口。
- 重复文档去重，内容变更保存历史版本；访问失败写入 crawl_runs，不冒充成功无记录。
- GitHub Actions 按小时执行，或在 Actions 手动运行 Collect customer intelligence 并填写集团编号。所谓实时是手动发起后待任务完成再刷新，不保证秒级或所有网站覆盖。
- Workers 仅提供公开只读查询，爬虫在 GitHub Actions 中执行，不受免费 Workers 10ms CPU 的解析限制；需要关注 Actions 自身额度。
- 已核实来源自动复查；新增客户可以匹配来源库或严格识别政府官网。其他企业网站保持候选，需核实后加入来源库。

## 本地验证

```sh
python intelligence/collector.py --sqlite /tmp/customer-intelligence.sqlite
python3 -m unittest discover -s tests -v

```

本地 SQLite 仅用于开发验证，不会自动同步到云端 D1；采集数据不提交 GitHub。SQLite 本地验证和云端部署验证分别报告。

## Cloudflare 免费方案启用步骤

1. 创建 Cloudflare 免费账号；Workers & Pages → D1 创建 customer-intelligence 数据库。
2. 从数据库控制台执行 schema.sql，或在 cloudflare 目录使用 Wrangler 执行 `wrangler d1 execute customer-intelligence --remote --file=../intelligence/schema.sql`。在 wrangler.jsonc 中填写实际 database_id。
3. 创建 Worker，部署 cloudflare/worker.mjs，并将 D1 绑定命名为 DB。设置 ALLOWED_ORIGIN 为 `https://changemkl.github.io`。可从 cloudflare 目录用 `wrangler deploy` 部署；本仓库没有自动执行部署，也没有假造 database_id。
4. 在 GitHub Actions Secrets 中添加 CLOUDFLARE_ACCOUNT_ID、CLOUDFLARE_D1_DATABASE_ID、CLOUDFLARE_API_TOKEN。Token 只授予该账号需要的 D1 编辑权限，保存到 Secrets，不发聊天、不写网页。
5. 将公开 Worker 地址填写在 public/profile-config.json 的 apiBaseUrl 中，如 `https://customer-intelligence.<你的子域>.workers.dev`。这个地址是公开配置，不是密钥。
6. 在 Actions 中手动运行 Collect customer intelligence。检查任务结果及 D1 数据，再检查公开接口 `/api/profiles?id=2100199365`。
7. 计划任务需要默认分支保留 collect-intelligence.yml；该工作流会检出 customer-workspace。网页每 5 分钟查询画像 API；修改名单后也会重新查询。

保持免费套餐，超额时停止请求，不自动订购付费方案。D1 免费额度为每天读 500 万行、写 10 万行、总存储 5GB；Workers 每天 10 万次请求（以官方账户当期规则为准）。数据库保留摘录和版本、不保存大文件；长期历史需根据实际使用增加清理策略。

目前没有配置 Cloudflare 凭据或部署线上画像 API。网页会显示“画像资料待接入”，不会用本地测试数据冒充线上数据。现有腾讯客户名单同步仍独立运行。


## 采集覆盖优化

- 根入口之外最多读取 2 个栏目列表，并发现机构职责、公司简介等概况页；每个来源最多读取 2 个概况页和 5 篇文章。
- 每篇资料单独进行客户名称或已配置别名匹配，不能仅凭导航短文本就挂到客户名下。
- 优先 ArticleTitle 元数据和正文标题，避免把“信息详情”等模板标题当新闻标题；保留明确的发布时间，未知时不编造。
- 首页/列表的中断响应只用于恢复已完整解析的文章链接；robots.txt 策略必须完整，文章正文中断则不入库。
- 按规范化 URL 去重；跨链接重复标题同时具有相同摘录才合并，避免把多篇“工作通知”误合并。
- 官网存在普通静态 JavaScript 跳转时，只解析明确的同域 location.replace 路径，不执行脚本、不解决验证码、不绕过登录。
- 政府机构和企业可能含有英文页面，按事先确认的名称别名匹配，保留原文，不自动翻译或推断业务结论。
- 自动保存前先 rebase 最新代码，避免采集时有人提交改版导致普通快进推送失败；冲突仍会中止，不覆盖人工修改。

## 已核验采购公告

`verified-procurement.json` 保存从上海市政府采购网公开记录逐项核对的公告、实际采购人、预算范围及计划采购月份。导出时按客户编号合并到独立快照，重复执行不会删除或重复添加这些记录。客户卡片直接展示项目标题和日期，标题链接原文，并支持关键词筛选；关联事业单位不归为委机关直接采购，综合服务预算不标成信息化专项金额，历史截止时间不表示当前可投标。当前官网采集并未自动复查这些采购公告的后续结果；保留的公告状态以原文为准。

## 日期筛选与公开招标

客户卡片以北京时间自动隐藏过去日期的采购意向。只公开采购月份的意向按月份比较，本月保留，不假设具体采购日。已知投标或响应截止时间的招标/磋商公告，截止后自动隐藏；公开标题的日期缺失时标明“采购日期未公开”，不认定为仍可投标；公告发布日期不作为采购日期。历史来源记录保留在独立快照，不作为有效商机显示或计数。

采集任务额外检索上海市政府采购网近60天采购公告，每客户最多2页，核对采购人名称后读取公开招标正文。采购意向及信息化招标的公开标题可独立入库，不要求完整正文；已知过期的计划与截止时间继续过滤；竞争性磋商不标成公开招标。范围不覆盖所有企业招采平台，不保证完整性，文件获取期限及更正、终止信息以官方原文为准。

## 每客户采购来源

`sources.json` 的 `government_procurement` 决定是否查询上海政府采购平台；`procurement_sources` 单独配置官网栏目或企业平台。上海建工配置上海建工电子商务平台，中建八局配置云筑集采及官网，太湖局配置官网招标公告及中央采购公告；不再把上海政府采购网当作这三家的唯一来源。

各来源独立记录检查状态，失败不影响其他来源，历史证据继续保留。卡片底部提供采购来源链接，无法自动读取的来源显示“暂不可读”；这不表示客户没有采购。太湖局栏目入口由官网政务公开页面的招标公告 MORE 链接核实。上海建工平台归属依据上海国资委公开检索记录及平台公开署名，当前访问受限。

云筑匿名推荐列表的网页接口已核实，但该接口的 robots 规则禁止自动读取时，采集任务停止并保留人工入口。公开推荐列表不等于完整检索；`endTime`、`signUpEndDate` 不作为投标截止，未核实采购方式不标成公开招标，列表 amount 不自动认定为公告预算。静态栏目扫描也有页面与时间上限，不保证全量覆盖；登录、验证码、禁止访问和纯脚本列表不会绕过。

## 公开标题优先

采购意向、招标意向/计划和信息化招标公告可以仅凭公开列表标题展示，不要求取得登录后的正文。列表中的明确采购计划日期或截止时间会保留；报名截止与发布日期不替代采购或投标日期。日期不公开时显示“公开标题 · 有效期待确认 / 采购日期未公开”，并在30天未再次采集后隐藏。存在已核实日期的记录不会被缺失日期的新标题覆盖。

静态列表保留同行的标题、日期和采购人字段，按客户相关性关联；详情页登录、验证码或访问失败不丢弃已公开标题，不尝试账号授权、付费内容或验证绕过。上海建工脚本列表在公开页面允许读取、执行环境有 Chrome 时使用临时匿名浏览器渲染；云筑仍遵守其接口的自动读取规则。页面仍只列标题与日期，不增加展开详情。

历史招标结果从上海市政府采购网公开结果表格提取标项名称与中标供应商，不把采购代理、候选人或评审描述当成中标供应商。按已核实标项统计竞争对手 TOP3；同一公告同一标项同一供应商去重，保留分公司与子公司的区别。统计范围随该客户已收录的本级及下属单位结果而定，不能代表全部历史采购。每日任务保留详情字段并逐批补录新公告，无法确认的标项及供应商明确标注待核实。

公开资料补充：`public/customer-supplements.json` 保存逐条人工核实的官方政策、结果公告及合同佐证，通过客户编号和全称同时匹配。前端每五分钟读取，独立于腾讯表格和自动采集快照。结果按公告链接去重后计入历史与潜在伙伴；合同只补充对应结果的金额、期限和来源，不额外计次。政策不作为有效采购统计；追加采购的单一来源公示保留拟定供应商状态，不计为中标，不覆盖同名的往年结果。
